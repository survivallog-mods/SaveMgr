# 存档管理 Mod 可行性分析（2026-10-31）

> 实证基线：gamekb `2026-10-23_26157732`（dump.cs / E8 调用方扫描 scan_e8.js / 实盘存档目录时间戳）。
> 结论：**可行**——游戏在每日结算时自写"完整格式"日快照，mod 只需在那一刻字节级抄走，零格式风险；风险集中在"恢复"环节（见 B 方案验证文档）。

## 1. 游戏现状

**存档布局**（`%USERPROFILE%\AppData\LocalLow\LLS\SLGame\Saves\`，实测 76 文件）：

| 文件 | 写入时机（E8 实锤） |
|---|---|
| `Save_<时间戳>.bytes` 主档 + `.bak` | 退回主菜单（`BattleToMain`）、章节倒计时结束、结局、重生等大节点。**每日结算不写主档** |
| `Save_<名>.snap0~N.bytes` | **每日结算（日翻转）时写**，滚动窗口仅 4~6 格，旧天被覆盖 |
| `HistorySave.bytes` | 存档列表/全局进度 |

当日实盘印证：snap0@11:02、snap1@14:08、snap2@14:46、snap3@18:32（四次结算），主档 19:53 才写（退出时）。

**关键调用链**：

```
CountUpTimer.Update / CostTime（日翻转）
  ├─ CaptureRebirthDaySnapshot()        // dump.cs:416087
  │    └─ GameSaveManager.CaptureDaySnapshot(day)      // 公开常规方法 0x28D2640
  │         └─ CaptureDaySnapshotCore → SaveGameFileCore  // 写 .snapN
  └─ TriggerDaySettlement()             // 私有常规方法 0x26CBEE0
```

**游戏自带能力**：`TryRestoreDaySnapshot(daysBack)`（原生回溯，仅滚动窗口内）、`.bak` 单份回退、Steam Cloud 同步开启中。**空缺**：超 4~6 天的永久备份、自定义间隔、手动存档点——本 mod 填真空白。

**SaveGame()/SaveGameFileCore 调用方全表**（scan_e8.js）：

- `SaveGame()`(0x28E3430) 调用方 17 处：DynamicEventManager 危机点、CountUpTimer.CaptureRebirthDaySnapshot、三个 EndingManager、BattleToMain、GetStartEvent、TryCaptureCasualEntrySnapshot、WebGm、Reducer_Web_RebirthChoice、BattleMain（SettleBeliefPoints/TriggerSubGames/EndSubGamesInternal）、DataCollectionManager。
- `SaveGameFileCore()`(0x28E2410) 调用方 15 处：**CaptureDaySnapshotCore**、ClearPending* ×2、MarkPending* ×2、SaveCountDownEnd、SaveDataCollectionRecords、SaveGameEnd/GameOver、TryBegin* ×2、TryCaptureCasualEntrySnapshot、TryRestoreDaySnapshot。

## 2. 逐功能可行性

| 功能 | 可行性 | 方案与风险 |
|---|---|---|
| 结算时机挂接 | ✅ 高 | postfix `CaptureDaySnapshot`（公开常规方法，不触 async 铁律）。兜底 Ticker 轮询 `CountUpTimer.GetDay()`（公开）零补丁 |
| 间隔 N 天 | ✅ 高 | mod 侧计数，配置走 BepInEx Config + ModCenter |
| 自动存档内容 | ✅ 高 | 字节级复制游戏刚写的 snap。不解析 MemoryPack，格式免疫 |
| 手动存档 | ✅ 高 | 复制当前主档+最新 snap（新鲜度=上次结算）。"强制新鲜写入"（调 `SaveGame()`）有任意时点持久化风险，首期不做 |
| 备份列表/删除/导出 | ✅ 高 | 纯文件操作 |
| **恢复（回档）** | ⚠️ 中 | 见 B 方案验证文档——已静态验证通过 |

## 3. 方案对比

| 方案 | 恢复形态 | 侵入度 | 裁决 |
|---|---|---|---|
| A 纯外部备份器 | 关游戏后还原文件/新档名 | 最低 | 首期底盘 |
| B = A + 游戏内注入新档 | 原生读档列表出现备份入口（`AddHistoryEntry`） | 中 | 进首期（banner 承诺"一键回档"） |
| C 扩容原生快照 | patch `GetSnapshotSlotCount` 多给槽位 | 最高 | 否决：不提供永久备份、改行为风险大 |

## 4. 开工前三个实证点（不猜）

1. 写盘是否同步（`batchSaveDepth/deferredSaveFrame` 提示可能延迟合并帧）；
2. 全模式覆盖（休闲/普通/无尽 + `RebirthSnapshotSlots=0` 时锚点是否触发）；
3. snap 文件独立可读性实机验证（结构同构置信度高，规则 10 要求实机）。
